Кадр 3 · Подвох

Когда Подделывателю везёт

Атака сработает, если сойдутся три условия.

  1. Сайт узнаёт тебя по cookie, которые браузер отправляет сам.
  2. Есть действие, которое что-то меняет: перевод, смена почты или пароля.
  3. Все параметры известны заранее. Секретов в запросе нет: «кому» и «сколько» злодей пишет сам.

Ответ Подделыватель не увидит. Политика одного источника не даёт котикам прочитать ответ банка. Поэтому CSRF — про чужие действия, а не про кражу данных.

Кадры 8–10 · Защита

Как закрыть дверь

  • CSRF-токен. Сервер кладёт в свою форму случайный секрет и проверяет его при каждом изменяющем запросе. Котики этот секрет не знают.
  • SameSite=Lax или Strict. Браузер не прикладывает cookie к POST-формам и фоновым запросам с чужих сайтов.
  • Проверка Origin. Браузер сам сообщает, откуда пришёл запрос. Сервер отклоняет изменяющие запросы с чужих источников.
  • GET никогда ничего не меняет. Lax пропускает cookie при переходе по ссылке и GET-форме, так что переводы — только POST.
  • Повторный пароль для самых важных действий.

Если на сайте есть XSS, скрипт внутри сайта прочитает любой CSRF-токен и отправит запрос сам. Поэтому XSS серьёзнее: он ломает защиту от CSRF.

Главное правило выпуска

Браузер прикладывает cookie сам. Запрос должен доказать, что он твой.

ВОПРОС С СОБЕСЕДОВАНИЯ · JUNIOR AppSec

«Объясни разницу между CSRF, CORS и политикой одного источника»

Подумай сам. Одно из трёх — правило браузера, второе — исключение из него, третье — атака. Кто здесь про чтение, а кто про отправку?

  1. Политика одного источника — правило браузера. Скрипт одного сайта не может читать ответы другого источника. Источник — это схема, домен и порт.
  2. CORS — ослабление этого правила. Сервер заголовками явно разрешает выбранным сайтам читать свои ответы. Он про чтение, а не про отправку.
  3. CSRF — атака на отправку. Чужой сайт заставляет браузер жертвы отправить изменяющий запрос с её cookie. Ответ атакующий не прочтёт, но действие уже выполнено.
  4. Защита от CSRF. CSRF-токен, SameSite=Lax или Strict, проверка Origin, GET без побочных эффектов. И никакого XSS: он обходит токены.

Ошибка новичка: «У нас настроен CORS, значит, CSRF не страшен». Обычная форма уходит без всяких проверок CORS.

Шпаргалка · выпуск №5

Что важно знать

  1. CSRF — чужие руки

    Чужой сайт заставляет твой браузер отправить запрос от твоего имени, а cookie браузер прикладывает сам.

  2. Ответ злодей не увидит

    Политика одного источника не даёт чужому сайту прочитать ответ, поэтому CSRF — про действия, а не про кражу данных.

  3. CSRF-токен — главный замок

    Сервер кладёт в форму случайный секрет и проверяет его при каждом изменяющем запросе.

  4. SameSite=Lax держит cookie дома

    С чужих сайтов cookie не едет в POST-формы и фоновые запросы, а Strict не пускает её даже при переходе по ссылке.

  5. CORS тут ни при чём

    CORS решает, кто может читать ответы, а обычная форма уходит и без него.

  6. GET ничего не меняет

    Переводы и смена почты — только POST с токеном и проверкой Origin.

  7. XSS ломает защиту

    Скрипт на самом сайте прочитает токен; SAST ищет отключённую защиту от CSRF во фреймворке, DAST проверяет токены и SameSite.

Тренируйся легально: раздел CSRF в PortSwigger Web Security Academy, OWASP Juice Shop, picoCTF. Трогать чужие сайты без разрешения нельзя.

Что такое CSRF?

Вопрос с собеседования

Объясни разницу между CSRF, CORS и политикой одного источника.

Политика одного источника — правило браузера: скрипт одного сайта не может читать ответы другого. CORS — способ, которым сервер явно разрешает определённым сайтам читать свои ответы, то есть ослабление этого правила. CSRF — атака, при которой чужой сайт заставляет браузер жертвы отправить изменяющий запрос с её cookie: прочитать ответ он не может, но действие выполняется. Защита от CSRF: токены, SameSite=Lax или Strict, проверка Origin, GET без побочных эффектов.

Практиковаться можно только там, где это разрешено: picoCTF, PortSwigger Web Security Academy, OWASP Juice Shop. Чужие сайты без разрешения трогать нельзя.
