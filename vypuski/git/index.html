Папка проекта с таким журналом называется репозиторий.

Коммит — это вагон

Каждое сохранение в Git — коммит. Это снимок всего проекта с подписью: кто, когда и зачем.

Вагон прицеплен к предыдущему, поэтому коммиты выстраиваются в поезд — историю проекта. А на борту у вагона номер — хеш: отпечаток из 40 символов. Обычно показывают первые 7.

Хеш считается из содержимого вагона и номера предыдущего.

Стр. 3

Станция origin

СоняА если я пролью чай на ноутбук?
Дядя МишаЯ тридцать лет проливаю — и ничего. Потому что копия лежит на сервере.

Сервер — GitHub, GitLab или свой — хранит удалённый репозиторий. По умолчанию он зовётся origin.

У каждого в команде полная копия со всей историей.

↓git clone

Скачать весь репозиторий со всей историей. Один раз, в начале.

↓git pull

Забрать новые вагоны с сервера и прицепить к своим.

↑git push

Отправить свои вагоны на сервер.

Если на сервере есть вагоны, которых нет у тебя, обычный push откажет.

Сначала pull, потом push. Это не вредность Git, а защита чужой работы.

Стр. 4

Вечный багаж

СоняЯ случайно закоммитила файл с паролем. Удалю его — и всё?
Дядя МишаНет. Коммит без файла — это новый вагон. А старый так и едет в истории — у всех, кто сделал clone.
Что делать, если в истории оказался ключ, — подробно в выпуске №8 →

Файл .gitignore

.env          # пароли и ключи
node_modules/ # библиотеки
build/        # сборка
*.log         # журналы

Список того, что Git не возьмёт в вагоны. Работает только для новых файлов: уже закоммиченный файл он из истории не уберёт.

Стр. 6

Подпись и КПП

Форс-ПушерТогда подпишу коммит именем Дяди Миши. Git поверит!
git config user.name "Дядя Миша"
Дядя МишаИмя автора — просто текст из настроек. А подписанный коммит заверен моим ключом.

Подпись ставят ключом GPG или SSH. Платформа покажет у коммита Verified, а защиту ветки можно настроить так, что без подписи в main не попасть.

Почему DevSecOps начинается в Git

Всё проходит через Git. Значит, и защита.

  1. Всё лежит в репозитории. Код, настройки серверов и сам конвейер сборки.
  2. Каждое изменение — коммит. На него можно повесить проверку: перед коммитом, в pull request, в CI.
  3. Pull request — это КПП. Ревью человека плюс автопроверки: тесты, SAST, SCA, поиск секретов.
  4. История — журнал расследований. Видно, кто, что и когда поменял.

Сам конвейер тоже под защитой: файлы CI меняются только с ревью ответственных (CODEOWNERS). Карта всех постов проверки — в выпуске №8.

Вопрос с собеседования

Как защитить главную ветку репозитория? И почему безопасность начинается в Git?

Подумай сам. Подсказка: вспомни, что не смог сделать Форс-Пушер после замка, и через какой КПП прошёл его фикс.
Защита ветки. В main нельзя пушить напрямую, нельзя делать force push и удалять ветку. Правила действуют и для админов.
Только через pull request. Минимум одно одобрение ревьюера, для важных файлов — владельцы кода (CODEOWNERS). После новых правок одобрение сбрасывается.
Обязательные проверки. Pull request не вливается, пока не прошли тесты, SAST, SCA и поиск секретов.
Почему Git. Через репозиторий проходят код, настройки и конвейер. Каждое изменение — точка для проверки, история — журнал аудита. Сверху — подписанные коммиты, MFA и минимум прав.

Ошибка новичка: «репозиторий приватный, значит, всё безопасно». Force push и плохой код приходят от своих, у которых доступ уже есть.

Шпаргалка

Шпаргалка: что важно знать

  1. 01
    Коммит — снимок с отпечатком

    Хеш считается из содержимого и родителя: поменяй букву — изменится номер.

  2. 02
    Ветка — табличка

    Это указатель на последний коммит, поэтому создать ветку почти ничего не стоит.

  3. 03
    Конфликт решает человек

    Если двое поменяли одну строку, Git останавливает слияние и ждёт твоего выбора.

  4. 04
    История — навсегда

    Удалённый файл остаётся в старых коммитах и во всех копиях, подробно — в выпуске №8.

  5. 05
    .gitignore — до коммита

    Он не даёт добавить новые файлы, но уже закоммиченное не уберёт.

  6. 06
    Force push в общую ветку — нет

    Он стирает чужие коммиты из ветки, поэтому защита main его запрещает.

  7. 07
    В main — только через КПП

    Pull request, ревью и зелёные проверки, а подпись доказывает, кто автор.

Вопрос с собеседования

Как защитить главную ветку репозитория и почему безопасность начинается в Git?

В main запрещены прямой push, force push и удаление, причём и для админов. Изменения попадают туда только через pull request с одобрением ревьюера (для важных файлов — владельцев кода из CODEOWNERS) и обязательными проверками: тесты, SAST, SCA, поиск секретов. Дополнительно — подписанные коммиты, MFA и минимум прав. Начинать с Git правильно, потому что через репозиторий проходят код, настройки и сам конвейер: каждое изменение — точка проверки, а история — журнал аудита. Ошибка новичка — считать, что приватного репозитория достаточно: опасные изменения приходят и от своих.

Практиковаться можно только там, где это разрешено: picoCTF, PortSwigger Web Security Academy, OWASP Juice Shop. Чужие сайты без разрешения трогать нельзя.
