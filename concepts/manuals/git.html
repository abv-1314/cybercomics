Git: тетрадь выживания

Конспект для тех, у кого в папке лежит sapyor_final_v7_TOCHNO.zip. Больше так не надо.

Git в одну строчку

Git — программа, которая ведёт журнал всех версий проекта: кто, что, когда и зачем поменял. К любой версии можно вернуться, а вдвоём (и вдесятером) можно работать над одним кодом и не затирать друг друга.

Словарик первой страницы

  • Репозиторий (repo) — папка проекта плюс скрытая папка .git, где живёт вся история. Удалишь .git — удалишь историю.
  • Рабочая папка — файлы, которые ты видишь и правишь прямо сейчас.
  • Индекс (staging area) — «корзина на кассе»: сюда ты складываешь изменения, которые пойдут в следующий коммит.
  • Коммит — сохранённый снимок проекта с подписью. Про него — следующая страница.

Зачем индекс, если можно сразу?

Чтобы собирать аккуратные коммиты. Поправил кнопку и опечатку в README? Сделай два коммита: git add только нужный файл — и коммить его отдельно.

1

1Коммит — это вагон

Каждый коммит — снимок всего проекта плюс подпись: автор, время, сообщение и ссылка на предыдущий коммит. Коммиты сцепляются в цепочку, как вагоны в поезд (помнишь выпуск №18 про Git?).

У каждого коммита есть хеш — отпечаток из 40 символов вроде 9e4b021c…. Обычно хватает первых 7. Хеш считается из содержимого и из хеша предыдущего коммита, поэтому тихо подменить старый коммит нельзя: поменяешь хоть букву — у него и у всех следующих будут новые номера.

Первый раз на компьютере

git config --global \
  user.name "Соня"
git config --global \
  user.email "sonya@example.com"

Это просто текст, который попадёт в коммиты. Проверки, что ты правда Соня, тут нет. Для этого есть подпись коммитов ключом.

Цикл, который ты будешь делать сто раз в день

# сделать из папки репозиторий (один раз)
git init
# что поменялось? что в индексе?
git status
# положить файл в индекс
git add game.js
# сохранить снимок с подписью
git commit -m "Мины: 12 вместо 10"
# история, по строчке на коммит
git log --oneline

плохо: fix, asdf, правки

Через месяц ты сам не поймёшь, что тут было.

хорошо: Счётчик мин не уходит в минус

Что изменилось и зачем. Коротко, как заголовок.

Правило отличника

Перед каждым коммитом — git status и git diff --staged. Две секунды, а ловят и случайный файл, и пароль, который чуть не уехал в историю.

2

2Ветка — это закладка

Ветка — не копия проекта, а подвижная табличка на последнем коммите линии. Сделал новый коммит — табличка сама переехала на него. Поэтому ветки в Git дешёвые: создавай сколько хочешь.

HEAD — «ты здесь» на карте: на какой ветке ты сейчас стоишь. Главная ветка обычно называется main (в старых проектах — master).

# создать ветку zvuk и перейти в неё
git switch -c zvuk
# вернуться в main
git switch main
# список веток, текущая со звёздочкой
git branch

В старых шпаргалках вместо switch пишут git checkout. Работает тоже, но switch понятнее: он только переключает ветки.

Зачем ветки

Эксперимент сломался — просто бросаешь ветку. А main всё это время оставался рабочим. В командах в main вообще не пишут напрямую: только через ветку и pull request с ревью.

3

3Merge: сливаем ветки

Merge (слияние) забирает коммиты другой ветки в текущую. Встаёшь туда, куда вливаешь, и называешь, что вливаешь:

git switch main
git merge zvuk
  • Fast-forward — в main ничего нового не было, табличка main просто переехала вперёд.
  • Коммит слияния — обе ветки ушли вперёд, Git склеил их новым коммитом с двумя «родителями».

Конфликт — это не авария

Если двое поменяли одну и ту же строку по-разному, Git не будет угадывать. Он остановится и покажет обе версии прямо в файле:

<<<<<<< HEAD
const MINES = 15; // Петя
=======
const MINES = 12; // Соня
>>>>>>> zvuk
  1. Открой файл, реши, что правильно (можно взять одно, другое или сделать третье).
  2. Удали строки-маркеры <<<, ===, >>>.
  3. git add game.js, потом git commit — слияние закончено.

Испугался? git merge --abort вернёт всё, как было до merge.

Конфликтов меньше, если

ветки короткие (день-два, а не месяц), ты часто забираешь свежий main и договариваешься в команде, кто какой файл трогает.

4

4Remote: копия на сервере

Remote — удалённый репозиторий на GitHub, GitLab или своём сервере. Главный обычно зовётся origin. Пролил чай на ноутбук — код цел. И у каждого в команде полная копия со всей историей.

КомандаЧто делает
git clone URLСкачать репозиторий целиком, с историей. Remote origin настроится сам.
git fetchУзнать, что нового на сервере. Твои файлы не трогает.
git pullfetch + слияние с твоей веткой. Забрал и применил.
git pushОтправить твои коммиты на сервер.
git push -u origin zvukПервый push новой ветки. -u запоминает пару «моя ветка ↔ ветка на сервере», дальше хватит git push.

push отказал? Это защита, а не вредность

Значит, на сервере есть коммиты, которых нет у тебя. Сделай git pull, разберись с конфликтами, потом git push. Не лечи это через --force: так стираются чужие коммиты. Злодей выпуска №18 так и делал.

5

5.gitignore: не бери это в вагон

Файл .gitignore в корне проекта — список того, что Git не должен замечать: секреты, библиотеки, сборки, журналы, мусор редактора.

# секреты и локальные настройки
.env
*.pem
# то, что можно скачать или собрать заново
node_modules/
build/
# журналы, но один пример оставим
*.log
!example.log
# только папка tmp в корне, не во вложенных
/tmp/
ЗаписьЗначит
#Комментарий.
*.logВсе файлы, которые кончаются на .log, в любой папке.
build/Слэш в конце: только папки с таким именем.
/tmp/Слэш в начале: только в корне проекта.
!example.logВосклицательный знак: «а вот этот всё-таки бери».

Главная ловушка

.gitignore работает только для файлов, которые Git ещё не отслеживает. Если .env уже был в коммите, запись в .gitignore его из истории не уберёт. Перестать отслеживать файл (сам файл останется у тебя на диске):

git rm --cached .env
git commit -m "Не отслеживать .env"

А если в том файле был пароль или ключ, его надо считать украденным. Это страница 8.

Лайфхак: заведи .env.example с именами переменных без значений. Его коммитить можно и нужно, чтобы команда знала, что заполнить.

6

6Аптечка: «я всё сломал»

Сначала вдохни. В Git почти всё, что было закоммичено, можно вернуть. Найди свою беду в таблице.

БедаЛекарство
Испортил файл, ещё не делал addgit restore game.js — вернёт версию из последнего коммита. Твои правки в нём пропадут.
Сделал add не тому файлуgit restore --staged game.js — вынет из индекса, правки останутся.
Опечатка в сообщении последнего коммита или забыл файлgit add забытый.js, потом git commit --amend. Только если ещё не делал push.
Последний коммит был лишним, push ещё не делалgit reset --soft HEAD~1 — коммит исчезнет, правки останутся в индексе.
Плохой коммит уже на сервереgit revert a1b2c3d — новый коммит, который отменяет тот. История не переписывается, команде ничего не ломаешь.
Сделал reset и потерял коммитgit reflog — журнал всех мест, где был HEAD. Найди хеш и сделай git switch -c spasenie хеш.
Надо срочно переключиться, а работа не законченаgit stash — спрятать правки, git stash pop — достать обратно.

revert = безопасно

Добавляет коммит-«антидот». Подходит для всего, что уже ушло на сервер.

reset --hard = опасно

Стирает незакоммиченные правки без корзины. Их не вернёт даже reflog. Прежде чем нажать Enter, сделай git status.

HEAD~1 — «коммит перед текущим», HEAD~2 — на два назад.

7Секреты в Git: вечный багаж

Секрет — всё, что открывает доступ: пароль от базы, ключ от облака или API, токен бота, приватный ключ. Его место — не в коде.

Почему «удалю файл — и всё» не работает

  1. Коммит без файла — это новый вагон. Старый, с ключом, так и едет в истории.
  2. Историю уже скачали все, кто делал clone или pull, а ещё форки и копии.
  3. Публичные репозитории постоянно читают боты, которые ищут ключи. Найти свежий ключ им хватает минут.

Ключ утёк? Порядок действий

  1. Отозвать и заменить ключ. Сразу, это шаг номер один.
  2. Проверить журналы: пользовался ли кто-то ключом и что успел сделать.
  3. Убрать последствия: чужие ресурсы, лишние доступы.
  4. Почистить историю (например, git filter-repo). Это уборка, а не защита: копии уже есть.
  5. Поставить контроль, чтобы не повторилось.

Как не допустить

  • Секреты — в переменных окружения или в хранилище секретов. В коде только имя: process.env.DB_PASSWORD.
  • .env — в .gitignore с первого дня проекта.
  • Проверка перед коммитом (pre-commit hook, например gitleaks) и поиск секретов в CI. Хук живёт только на твоём компьютере и обходится флагом --no-verify, поэтому вторая линия в CI обязательна.
  • На GitHub можно включить secret scanning и push protection: сервер сам остановит push с похожим на ключ текстом.

8Шпаргалка: каждый день

Каждая команда с расшифровкой флагов. Слова в <скобках> замени на своё.

git status -s

Что изменилось и что лежит в индексе.

  • -s (short) — коротко, по строчке на файл: M изменён, A добавлен, ?? Git о нём не знает.
git add <файл> · git add -p

Положить изменения в индекс.

  • -p (patch) — показывает правки по кусочкам и спрашивает про каждый: y взять, n пропустить. Лучший способ собирать аккуратные коммиты.
  • git add . — всё в текущей папке. Удобно, но сначала посмотри status.
git commit -m "<сообщение>"
  • -m (message) — сообщение прямо в команде. Без него откроется редактор.
  • --amend — переделать последний коммит (только до push).
git diff · git diff --staged
  • Без флагов — что поменялось, но ещё не в индексе.
  • --staged — что уже в индексе и уйдёт в коммит.
git log --oneline --graph --all
  • --oneline — по строчке на коммит: короткий хеш и сообщение.
  • --graph — рисует ветки и слияния палочками.
  • --all — показать все ветки, а не только текущую.
git switch -c <ветка>
  • -c (create) — создать ветку и сразу перейти. Без -c — просто перейти.
git branch -d <ветка>
  • -d — удалить ветку, если она уже влита. Git не даст потерять работу.
  • -D — удалить в любом случае. Большая буква — большая ответственность.

9Шпаргалка: сервер и откаты

git clone <адрес> <папка>
  • Папку можно не писать: возьмётся имя репозитория.
git pull · git pull --rebase
  • Обычный pull сливает изменения с сервера с твоими (может появиться коммит слияния).
  • --rebase — переставляет твои ещё не отправленные коммиты поверх свежих с сервера. История получается ровной линией.
git push -u origin <ветка>
  • origin — куда отправить, <ветка> — что отправить.
  • -u (set upstream) — запомнить связь, дальше хватит git push.
git push --force-with-lease
  • Иногда переписать ветку на сервере нужно, например свою личную ветку после rebase. Этот флаг откажет, если там появились чужие коммиты, которых ты не видел. Голый --force сотрёт их молча.
  • В main — никогда. Пусть защита ветки на сервере это запрещает.
git restore <файл> · git restore --staged <файл>
  • Без флага — вернуть файл к последнему коммиту (правки пропадут).
  • --staged — только вынуть из индекса.
git reset --soft | --mixed | --hard HEAD~1
  • --soft — убрать коммит, правки остаются в индексе.
  • --mixed (так по умолчанию) — убрать коммит, правки остаются в файлах, но не в индексе.
  • --hard — убрать коммит и правки. Осторожно!
git revert <хеш> · git reflog · git stash
  • revert — отменить коммит новым коммитом. reflog — где был HEAD. stash — спрятать правки на время.
