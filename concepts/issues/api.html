Дядя МишаКак так вышло? Представь пункт выдачи. В нём три участника.

    

  

  

    

      Клиент
      ТЫ
      
Браузер или приложение. Просит и показывает. Целиком в руках того, кто держит телефон.

    

  

  

    

      API
      ОКНО
      
Окошко выдачи. Правила: что можно попросить и в каком виде получить ответ.

    

  

  

    

      Сервер
      СКЛАД
      
Компьютер компании. Там база: все посылки, телефоны, адреса. И все проверки.

    

  

  

    

      
API — Application Programming Interface, «интерфейс для программ». Так одна программа просит что-то у другой.

      
СоняА Болтун тогда кто?

      
Дядя МишаОкошко, которое на вопрос «как меня зовут?» выносит со склада всю коробку. С чужими вещами в придачу.

    

  

  

    

      
Всё, что ушло клиенту, — уже не секрет.

      
Данные, код, ключи: их можно открыть, прочитать и подменить. Поэтому проверки и фильтры живут только на сервере.

      429
    

  

  

    

      
Rate limiting — ограничение частоты: не больше N запросов в минуту с одного токена или адреса. Лишние получают ответ 429 Too Many Requests.

      
Лимиты спасают не только от перебора: без них злодей скачает базу запрос за запросом или завалит сервер.

Ещё три правила склада

      
Проверяй владельцаНа каждый запрос к заказу, профилю, файлу: принадлежит ли он владельцу токена.

      
Фильтруй входПринимай только ожидаемые поля. Иначе кто-то пришлёт "role": "admin" — это mass assignment.

      
Опиши ответСхема API (например, OpenAPI) фиксирует поля ответа. Автотест ловит лишние.

Собеседование



  
Вопрос с собеседования

  
API отдаёт пользователю его профиль. Какие две главные ошибки здесь бывают и как их найти?

  
Подумай сам. Подсказка: одна ошибка — «отдал лишнее», другая — «отдал чужое». И где должна жить защита?

  
  

    
Лишние поля. Сервер сериализует объект из базы целиком, а клиент «прячет» ненужное. Хеш пароля, телефон, связанные записи видны в ответе. В OWASP API Top 10 это API3:2023.

    
Чужой объект. BOLA, API1:2023: сервер проверяет токен, но не владельца. Меняешь id в запросе — получаешь чужие данные.

    
Исправление. Только на сервере: ответ собирается по списку разрешённых полей, на каждый объект — проверка владельца. Плюс rate limiting, чтобы id нельзя было перебирать.

    
Как найти. Смотреть сырые ответы в DevTools или прокси, а не экран. Два тестовых аккаунта: запросить объекты одного токеном другого. В CI — тесты авторизации и проверка ответа по схеме OpenAPI.

    
Ошибка новичка: «приложение же не показывает эти поля» или «у нас id длинные, не угадают». Защита на клиенте и сложные id — не проверка прав.
