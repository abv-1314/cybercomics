ЧТО РАЗРЕШЕНО НА students И grades

Дневнику нужно только показывать и ставить оценки. Исправления делает завуч под своей учёткой.

-- владельцу GRANT не нужен: ему можно всё
  • Своя учётка у каждого приложения. Администратор входит под своей, и не из кода сайта.
  • Права не чинят дыру. SELECT у дневника есть — значит, через ту же дыру оценки ещё можно прочитать. Закроем её в атаке 4.
  • Базу не выставляют в интернет. Порт закрыт, подключаться можно только с сервера приложения.

ХешВ одну сторону. Обратно не превратить. Сайт хеширует введённый пароль и сравнивает хеши.

ШифрВ обе стороны: с ключом данные читаются. Для того, что нужно прочитать.

  • Соль. Случайная добавка к каждому паролю. У двух родителей пароль qwerty123, а хеши разные — готовые таблицы подбора не помогут.
  • Медленный хеш. Для паролей — Argon2id или bcrypt. Быстрые хеши вроде MD5 и SHA-256 для паролей не годятся: их перебирают миллиардами в секунду.
  • Ключ — не рядом с замком. Ключ шифрования хранят отдельно от базы, в хранилище секретов. Диски и бэкапы тоже шифруют.

ДРОП ТАБЛЫЧНе читается? Тогда никому. Ночью зашифрую сервер школы и всё, до чего он дотянется. Хотите базу — платите.

КУДА КЛАСТЬ НОЧНЫЕ КОПИИ · выбери места

1 из 3 копий 1 из 2 носителей 0 из 1 вне здания

Правило 3-2-1: три копии данных (рабочая и ещё две), на двух разных носителях, одна — вне здания.

  • Бэкап, который ни разу не восстанавливали, — не бэкап. Восстановление проверяют по расписанию, на отдельном сервере.
  • 3-2-1-1-0. Современный вариант: ещё одна копия офлайн или неизменяемая и ноль ошибок при проверке.
  • Сервер может дописать копию, но не стереть. Иначе вирус с сервера сотрёт и бэкапы.

Как защитить базу данных веб-приложения? Назови слои.

Подумай сам

Представь, что злодей уже может слать запросы от имени приложения. Что ограничит вред? А если он унесёт копию? А если всё сотрёт?

  1. Закрыть вход. Только параметризованные запросы или ORM, без склейки строк. Саму базу не видно из интернета: доступ только с сервера приложения, соединение по TLS.
  2. Минимальные права. У каждого приложения своя учётка и только нужные операции на нужные таблицы. Приложение не владелец, DROP ему недоступен. Админы входят отдельно, с MFA.
  3. Утечка должна быть бесполезной. Пароли — медленный хеш с солью (Argon2id, bcrypt). Чувствительные поля шифруют, ключ хранят вне базы. Диски и бэкапы тоже зашифрованы.
  4. Готовность к худшему. Бэкапы по правилу 3-2-1, одна копия неизменяемая или офлайн, восстановление регулярно проверяют. Журнал запросов и тревога на массовую выгрузку.

Ошибка новичка: сказать «у нас есть бэкап» — и ни разу его не восстановить. Или «база внутри сети, её никто не видит».

Шпаргалка: что важно знать

  1. 01
    Таблица = строки × столбцы

    Строка — одна запись, столбец — одно свойство у всех записей.

  2. 02
    Первичный и внешний ключ

    id не повторяется и указывает ровно на одну строку. Внешний ключ ссылается на чужой id, а JOIN склеивает по нему таблицы.

  3. 03
    SELECT, WHERE, ORDER BY

    Что показать, какие строки, в каком порядке. INSERT добавляет строку.

  4. 04
    UPDATE и DELETE без WHERE

    Задевают каждую строку. Сначала SELECT с тем же WHERE, потом BEGIN … COMMIT, а при ошибке — ROLLBACK.

  5. 05
    База — главная добыча

    Утечка — это выгруженные таблицы. Поэтому защищают саму базу, а не только сайт.

  6. 06
    Параметры и минимальные права

    Запросы только с параметрами. Приложению — свои права только на нужные таблицы, без DROP.

  7. 07
    Хеш, шифр, бэкап 3-2-1

    Пароли хешируют с солью, телефоны шифруют, копии хранят по правилу 3-2-1 и проверяют восстановление.

Тренируйся легально: собери свою базу на SQLite у себя на компьютере, решай задачи picoCTF, PortSwigger Web Security Academy (раздел SQL injection) и OWASP Juice Shop. Чужие базы и сайты трогать нельзя.
